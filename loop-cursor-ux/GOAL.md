## User report (verbatim intent)
With a **cursor CLI (cursor-native) session as the MAIN/top-level session** — trio sub-agent cursor sessions are fine:
1. Assistant content often does not render in the web UI at all.
2. When it does render, it appears ABOVE the user's own message.
3. "Something went wrong" appears **every time the normal (chat) UI is opened**, as opposed to the tmux/terminal view — not tied to a turn failing.

## Diagnosis already established (verified against code, live logs and a read-only chat.db) — do NOT re-derive, but DO reproduce
**Symptom 1 — confirmed, client-side.** `cursor_native_executor.py:105-114` injects the text into tmux and immediately yields `TurnComplete(response=None)` (`supports_streaming()` is False, `:61-63`), so a top-level turn completes in milliseconds while Cursor keeps generating for minutes. The store flips `activeResponse` to `completed` with `completedAt = Date.now()` (`web/src/store/chatStore.ts:6079`). `tapLiveDeltas` then drops every later delta and permanently blacklists its message id once `isStaleCompletedResponse` is true (`chatStore.ts:4427-4433`, predicate at `:4495-4501`, `REVIVE_WINDOW_MS = 15_000` at `:4489`). The live id is stable for the whole Cursor turn (`cursor-live-<session>-<epoch>`, minted once per epoch at `omnigent/cursor_native_stream.py:161-164`), so one stale check blackholes the entire response. Cursor usually spends >15 s on tool chrome before its first prose line, hence "often". Sub-agents are unaffected: no web-driven send, so `activeResponse` is never slammed to completed at t≈0.
**Symptom 2 — confirmed, client-side.** The user's own message is deliberately held off `blocks` while pending (`chatStore.ts:18`, `:244`) and only committed on `session.input.consumed` by **tail append** (`chatStore.ts:5652-5662` and `:5687-5697`). For cursor that event can only fire once the mirrored user row reaches the server (`omnigent/cursor_native_forwarder.py:804-820`, driven from `:1157-1162`) — 1-3 s later — while the live assistant block was already tail-appended on the first pane delta (`chatStore.ts:4331-4335`). Commit 9beb255aa deliberately streams pane text *before* the store row lands, so the assistant block wins the race. Persisted DB order is correct (`position`/`created_at` are monotone, user before assistant), so a reload shows the right order — this is purely the live view.
**Symptom 3 — confirmed cause.** Opening the chat view re-pins the model: the live server log (`~/.omnigent/logs/server/server-20260828-215638-205925.log`) shows session `6511d33969cb45d9a6af3c85fec3b856` receiving a burst of **GETs only** (snapshot, agent, terminals, child_sessions, items, stream — i.e. a view open, no message send) followed at 22:20:12.800 by `Session-change forward rejected … type='model_change' status=503 body={"error":"cursor_native_model_failed"…}` and `Model change not applied to the terminal … model='cursor-grok-4.6': the runner returned status 503`. The runner side is `_handle_cursor_native_model_change` (`omnigent/runner/app.py:4436-4465`) → `inject_model_command` (`omnigent/cursor_native_bridge.py:884`), which fails with "cursor model 'cursor-grok-4.6' did not resolve to its exact picker row; the model was not switched". The UI then renders a failure block whose code `cursor_native_model_failed` is **absent** from `FAILURE_CODE_DESCRIPTIONS` (`web/src/components/blocks/StatusBlocks.tsx:61-71`), so `headline = title || FAILURE_CODE_DESCRIPTIONS[code] || "Something went wrong"` (`:149`) falls through to the generic string. Only a top-level session has a model picker, which is why sub-agents never show it. Relevant UI call sites: `web/src/pages/ChatPage.tsx:4911-4921` (picker change) and `:6248-6259` (`rePinAfterRouting || modelChanged` → `store.setModel`). Related runner noise: `Skipping non-injectable Cursor model id 'claude-4-sonnet'` (model-options filtering).

## Mission
Make a top-level cursor-native session render assistant text as it streams, below the user's message, and stop showing a turn-error card for a model re-pin that is not a turn failure — without regressing claude-native/codex streaming, the rAF deadline work (e06c3d264), or the cursor sub-agent path.

## Slices
1. **cursor-live-deltas** — a live delta for a native terminal harness whose turn completes at injection must not be dropped by the stale-completed gate. Preferred: bind the cursor forwarder's deltas/status to a response lifecycle so the bubble stays open (the `post_external_session_status(response_id=…)` contract documented at `omnigent/_native_post_delivery.py:189-196`; the forwarder posts `idle` at `cursor_native_forwarder.py:1281`). Acceptable narrower fix: exempt live message ids belonging to an external/native stream from `isStaleCompletedResponse`/`ignored` (never a blanket removal — the gate exists to stop scheduled-wake deltas leaking into a previous turn's bubble). Tests in `web/src/store/chatStore.test.ts`: a delta arriving >15 s after `completed` on a cursor-native session is applied; a scheduled-wake delta for a genuinely finished response is still ignored.
2. **cursor-live-order** — when `session.input.consumed` commits a user block, splice it **before** any trailing live block instead of appending (`chatStore.ts:5652-5662`, `:5687-5697`; `LIVE_ITEM_PREFIX` is already imported at `:57`). Test: with a live block present, the committed user block lands above it and text order matches the persisted order.
3. **cursor-model-repin** — (a) do not surface a failed *model re-pin* as a turn-error block at all: it is a session-config action, so it belongs in the model picker/toast, not the transcript; (b) do not re-pin on view open when the drafted model equals what is already applied (the `rePinAfterRouting` branch at `ChatPage.tsx:6248-6259` fires even when nothing changed — verify against the live evidence which path actually ran on open and fix that one); (c) add `cursor_native_model_failed` to `FAILURE_CODE_DESCRIPTIONS` with an accurate message (and to `describe_failure_code` in `omnigent/runner/launch_failure.py` if that table is the server-side twin — the comment at `StatusBlocks.tsx:58-60` says keep them in sync) so that if it ever does surface it reads honestly; (d) investigate cheaply whether `cursor-grok-4.6` failing to resolve to a picker row is a real bug in `inject_model_command` (`cursor_native_bridge.py:884`) worth fixing here or a separate follow-up — record the finding either way, fix only if small.
