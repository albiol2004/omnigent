## User decisions (verbatim intent)
1. "Anthropic key no please, only CLI models" — API-key providers must never be used for fork compaction by default.
2. "These CLIs already have a fork/branch function, why can't we reuse those?" — for native same-family forks, use the CLI's own fork and let the CLI manage context exactly as it does for the source session.

## Insight driving this loop (verified on the live machine)
A native→same-family fork (claude→claude, codex→codex, same host) does not need to shrink anything: a fork of a 782 kB transcript works exactly as well as the source session, which is alive at that size; Claude Code / Codex auto-compact at the next turn when needed. The 413s the user hit on that path came from OUR byte guard (`claude_native._clone_claude_transcript` → `guard_fork_context_bytes`, then the compact-on-fork server route + rendered-size estimate), not from the CLI. The "Prompt is too long" failures that started all this happen on the OTHER paths: claude-sdk replaying history as one prompt, and cross-family / no-native-transcript rebuilds (`_ensure_local_claude_resume_transcript` from Omnigent items). The CLIs' fork features: `claude --resume <id> --fork-session` (new session id from an existing transcript), `codex fork` (`codex --help`: "Fork a previous interactive session").

## Mission
Make a fork of a native claude/codex session on the same host launch as a plain CLI fork with no byte guard and no server-side summarization — while keeping the guard and a CLI-produced (never API-key) summary only for cross-family, SDK, and rebuild-from-items forks — verified by a real fork of the user's oversize session e34847899b7d47b3ad322948d4ea6002 on a throwaway server.
